# Кандидатогенерация для поиска услуг Авито

Для каждого из 2452 запросов нужно вернуть 50 объявлений из корпуса в 189 тыс. Метрика Recall@50.

Результат на платформе: **0.8812** (отправка №7). Локальная оценка на отложенной выборке: 0.898.

## Как устроено решение

```
кандидаты из нескольких каналов (~800 на запрос)
  -> CatBoost, топ-300
  -> cross-encoder bge-reranker-v2-m3
  -> CatBoost, топ-50
```

Каналы кандидатов (`src/channels/`, `src/candidates.py`):

- BM25 по заголовку, параметрам и описанию со стеммингом Snowball. Запрос склеивается с фильтрами поиска, потому что смысл запроса часто в них.
- Две dense-модели, multilingual-e5-base и USER-bge-m3, дообученные на парах «запрос, выбранное объявление» из train (одна эпоха, функция потерь CachedMultipleNegativesRankingLoss: остальные объявления батча служат негативами). Готовые модели плохо понимают жаргон услуг, дообучение дало около +3 п.п.
- Те же модели, но только среди объявлений в радиусе 50 км от локации запроса. Без этого нужное объявление рядом с пользователем тонет среди похожих из других городов.
- Объявления, которые выбирали по похожим запросам в истории (TF-IDF по символьным n-граммам).
- Популярное в локации, чтобы всегда набиралось 50.

Первый ранкер (`src/ranker.py`) видит скоры и места кандидата во всех каналах, сходство с запросом, совпадение локации и расстояние, популярность в истории (в виде доли, так как объём истории на валидации и на тесте разный), вероятность подкатегории по похожим запросам, рейтинг, число отзывов и цену.

Второй этап (`src/stage2.py`): cross-encoder bge-reranker-v2-m3 без дообучения оценивает пары «запрос, объявление» для топ-300 первого ранкера. В отличие от dense-моделей он читает запрос и объявление вместе и точнее различает близкие по смыслу услуги, но работает медленно, поэтому применяется только к топу. В текст запроса и объявления добавлен город, иначе модель не учитывает географию. Второй CatBoost объединяет эту оценку с оценкой первого ранкера и несколькими сильными признаками первого этапа.

## Данные

Что выяснилось в EDA (`notebooks/01_eda.ipynb`) и повлияло на решение:

- в train нет времени и сессий, поэтому валидация строится по группам запросов;
- объявления из train почти не встречаются в корпусе (5%), поэтому историю можно использовать только через похожие объявления и признаки;
- в benchmark на каждый уникальный текст приходится один запрос, и 37% этих текстов есть в train; разбиение train повторяет это устройство;
- 83% выборов сделаны в локации запроса, поэтому локация используется как признак и отдельный канал, без жёсткого фильтра;
- поле категории почти константное и не используется.

## Валидация

train разбит на три части:

- P1 (около 96%): история, по ней считаются все исторические признаки и дообучаются dense-модели;
- P2 (8000 запросов): обучение ранкеров и подбор параметров;
- P3 (5000 запросов): отложенная проверка.

Запросы P2 и P3 выбираются так же, как устроен benchmark: один случайный запрос на уникальный текст. Для оценки к корпусу добавлены релевантные объявления P2 и P3.

Первая отправка (простой бейзлайн) дала 0.149 локально и 0.080 на платформе. Разница объяснилась двумя вещами: в P3 больше маленьких городов, где найти ответ проще, и P3 сильнее пересекается с историей. Поэтому запросы взвешиваются по доле их города в benchmark, а у 30% релевантных объявлений P2 и P3 история удаляется. После этого локальная оценка стабильно выше платформы примерно на 3 п.п. До №7 прогноз по этому правилу ошибался не больше чем на 0.5 п.п., №7 оказался на 1.3 п.п. выше прогноза.

Изменение принималось, только если 95% доверительный интервал разницы на P3 (парный бутстрэп по запросам) выше нуля. Параметры подбирались только на P2.

## Ошибки

Разбор 50 случайных промахов на P3 (ранкер №3, `analysis/error_analysis.py`):

| Тип ошибки | Доля | Что сделано |
|---|---|---|
| Тема найдена, но объявление в другом городе | 34% | dense-поиск в радиусе 50 км |
| Синоним или смежная услуга («инъекции липолитиков» и «процедура худое лицо») | 18% | дообучение dense-моделей |
| Нужное объявление найдено, но ниже 50-го места | 14% | cross-encoder, затем топ-300 |
| Шум разметки | 12% | ничего |
| Местные нерелевантные объявления вытесняют нужное | 8% | cross-encoder |
| Опечатки, слишком общие запросы, смысл только в фильтрах | 14% | частично: фильтры добавлены в текст запроса |

У финальной модели на P3 теряется 10.2 п.п. Recall@50: 5.1 п.п. приходятся на объявления, которые не попали в топ-300 первого ранкера, ещё 5.1 п.п. на ранжирование внутри топ-300.

## Что не помогло

- Дообучение cross-encoder на train: качество упало (0.884 до 0.850 на 1000 запросах P2).
- Второй cross-encoder Qwen3-Reranker-0.6B: слабее bge-reranker и примерно в 5 раз медленнее.
- Дополнительные признаки второго ранкера (совпадение фильтров, нормировка оценок, ансамбль): прирост в пределах шума.

## Воспроизведение

1. Положить три parquet-файла задания в `data/`.
2. Скачать архив артефактов https://disk.360.yandex.ru/d/E7s5xf-lJm-0NA (3.23 ГБ, md5 `a0ed0ac45b7ddbcd773d8d40060c4cce`) и распаковать в корень репозитория. В нём дообученные модели, эмбеддинги корпуса, ранкеры и оценки cross-encoder. Это производные данных задания, они выложены только для проверки.
3. Запустить:

```
python3.13 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python make_answer.py
```

Около 10 минут на MacBook M4. Получается `answer.csv` с md5 `b3de97da6a9a13a766c606e59c8587c6`, тот же файл отправлен на платформу.

Без архива всё можно пересчитать. Вычисления на GPU не детерминированы бит в бит, поэтому md5 в этом случае может отличаться.

| Шаг | Где | Время |
|---|---|---|
| `python -m src.split`, `python -m src.make_pairs` | локально | 5 мин |
| `notebooks/kaggle_1_train_e5.ipynb` (`SPEED_TEST = False`) | Kaggle | 1 ч |
| `notebooks/kaggle_2_train_bge.ipynb` | Kaggle | 3.5 ч |
| `python -m src.eval_channels` | локально | 25 мин |
| `python -m src.ranker e5baseft artifacts/e5-base-ft fix` | локально | 80 мин |
| `PYTHONPATH=. python analysis/dense_grid.py` | локально | 50 мин |
| `python -m src.stage2 first`, `pairs`, `depth` | локально | 50 мин |
| `notebooks/kaggle_3_score_reranker.ipynb` на местах 1-150 и 151-300 | Kaggle | 6 ч |
| `python -m src.stage2 train2 300`, `python make_answer.py` | локально | 10 мин |

Модель e5-small для весов RRF скачивается один раз: `python -c "from huggingface_hub import snapshot_download; snapshot_download('intfloat/multilingual-e5-small')"`.

## Структура

- `make_answer.py`: от данных и артефактов до `answer.csv`
- `src/`: данные, разбиение, метрика, каналы, ранкеры, второй этап
- `analysis/`: скрипты для цифр из этого описания
- `notebooks/`: EDA и ноутбуки для Kaggle
- `tests/`: тесты метрики, разбиения и формата ответа

## Модели и библиотеки

Модели: multilingual-e5-base и multilingual-e5-small (MIT), deepvk/USER-bge-m3 и BAAI/bge-reranker-v2-m3 (Apache-2.0).
Библиотеки: catboost, sentence-transformers, transformers, torch, bm25s, PyStemmer, scikit-learn, pandas, numpy, pyarrow (точные версии в `requirements.txt`). Внешних API нет.
